# ADR-001: Mobile-first FitFlow architecture

- **Date:** 2026-09-16
- **Status:** Proposed; requires prototype, cost, security and compliance validation.

## Context
The case study describes onboarding abandonment, nutrition friction, generic workout plans, private community needs, and accessibility/offline requirements.

## Decision
Use Expo React Native (mobile and web), NestJS API, FastAPI ML service, managed PostgreSQL, Cognito and scoped WebSockets. Add optional Redis/on-device inference only after testing.

## Alternatives
Flutter cross-platform; Kotlin Multiplatform; separate Swift/Kotlin; Firebase/Firestore-first backend; MongoDB; Go API.

## Rationale
Shared TypeScript workflow, familiar React web reuse, explicit authorization, relational integrity for workout/meal/group data and isolation of Python ML inference.

## Consequences
More service integration than all-Firebase, WebSocket operating cost, account/provider lock-in and model performance governance.

## Safeguards
Least privilege, privacy by default, no raw personal information in logs, short-lived photos, backup restore drills, AI edit/approval, and service-specific eligibility review for PHI.

## Revisit when
Accessibility/web/camera spike fails, expected billing changes, security validation fails or compliance requirements shift.
